# Expo Router owns deep links — don't add a second listener

Expo Router's native linking config ignores its own `prefixes` array (confirmed by reading `node_modules/expo-router/build/getLinkingConfig.js` and `fork/extractPathFromURL.js` for SDK 55) — `extractExpoPathFromURL` derives the route path from *any* incoming `https://` or custom-scheme URL, not just ones matching a declared prefix. So every deep link — cold-start *and* warm (app already running in background) — already gets routed to its matching file route (`app/**`) automatically, with no app code required.

App code must never add its own `Linking.addEventListener('url', ...)` that calls `router.push`/`router.replace` on the same event. `fork/useLinking.native.js` registers its own `'url'` listener to drive Expo Router's internal navigation dispatch. Two listeners on the same RN `Linking` emitter both fire for one event; whichever manual `router.push` happens first gets clobbered milliseconds later when Expo Router's own listener resolves the URL and dispatches/`resetRoot`s to the file-route path — the manual navigation is silently lost.

**Why:** This exact bug shipped in `apps/mobile/app/_layout.tsx`'s `AuthGate` — a custom `Linking.addEventListener('url', handleDeepLink)` was added (Phase 2, original invite-link implementation) to route already-authenticated users straight to `/trip/join-confirm` on an invite deep link. It happened to work on cold start only because Expo Router's *initial* route resolution runs before mount, before the manual listener's own `getInitialURL()` call resolves (deduped via a ref by the time it fires). On a warm start there is no such ordering luck: both listeners fire off the live `'url'` event, the manual `router.push` to join-confirm loses the race to Expo Router's own listener resetting to `/join`, and a downstream `handledInviteTokenRef` dedupe check then bounced the user to `/(tabs)` — the invite link appeared to do nothing. Fixed in v1.32.1 (see `git log -- apps/mobile/app/_layout.tsx`, "fix: warm-start invite deep links").

**How to apply:** For any native deep link that needs different in-app handling depending on app/auth state (invites, magic links, share targets, etc.), let it land on its normal file route and do the state-dependent redirect from a `useSegments()`-driven effect (the pattern already used in `AuthGate`'s main redirect effect) — never from a second `Linking.addEventListener`. Reserve manual `Linking.getInitialURL()` calls for genuine cold-start fallbacks only (Expo Router's own `getInitialURLWithTimeout` races a 150ms timeout and can lose the launch URL), and never pair them with a `Linking.addEventListener('url', ...)` subscription.
